Norm N10 requires every test script / V&V tool to be **qualified** per
ECSS-Q-ST-80C (tool and tool qualification) and ECSS-E-ST-40C (verification
tools derived from standards). For criticality B the minimum qualification of a
script-level tool is: source review + inspection + configuration management; a
change in the tool invalidates previously produced evidence until
re-qualification.

Independence of the qualification review is required when stated beside the
tool, or always when targeting criticality A (norm N9 profiles R2).

### NC-EXT-174 elaboration receipt (schema `nc-ext-174/2`)

The T6 gate consumes `verification/lean/.lake/build/elab_receipt.json`, produced only by `tools/scripts/lean_elab_receipt.py`. Required root fields: `schema_version` (`nc-ext-174/2`), `generator`, `generator_version` (must equal the consumer's own generator version), `generated_at` (UTC `YYYY-MM-DDTHH:MM:SSZ`), `lean_root`, `build_lib`, `lean_toolchain_sha256`, `lakefile_sha256`, `lake_manifest_sha256`, `lean_version`, `dependencies[]` (`name`, `path`, `manifest_present`, `manifest_sha256`), `config_sha256` over those values, `outputs_cleared` (`true`) and `elaboration_order` (the module names in the order they were elaborated). `modules` is a map keyed by module name (`Frick.<Path>`); each entry requires `source`, `source_sha256`, `olean` (must equal the canonical `build_lib/<Namespace>/<path>.olean` for that module name), `olean_sha256`, `olean_size`, `compiler_cwd` (must equal `verification/lean`), `compiler_argv` (must equal the canonical `lake env lean -o/-i` argv for that module), `elaboration_index`, `exit_status` (0) and `status` (`success`). `elaboration_order` must cover the inventory exactly and place every intra-namespace dependency before its importer; the producer refuses to write a receipt for a missing import target, a self-import or an import cycle. The consumer rejects a missing, symlinked, non-regular, unreadable or malformed receipt; an unknown schema; missing required fields; any source module absent from the receipt or any receipt module absent from the source; source/olean hash and size mismatches; empty, non-regular or out-of-tree olean outputs; toolchain/lakefile/lake-manifest/`config_sha256`/dependency mismatches; a `lean_version` that does not match the pinned toolchain tag; any non-success `status` or non-zero `exit_status`; and all symlink/cycle/inventory diagnostics. Diagnostic strings are stable and are printed by `trace.py` as `NC-EXT-174: <diagnostic>`.

Provenance limits: a receipt is evidence only of a successful run of the generator with the recorded inputs, in the recorded order, after the enumerated outputs were removed. The consumer cannot replay Lean and does not defend against a privileged actor who fabricates both source and outputs; it detects a receipt that does not match the current tree (source, olean, toolchain, configuration, dependency or ordering mismatch), a missing or malformed receipt, and an incomplete inventory. It does not evaluate the age of a receipt, and importing a stale olean is prevented by the producer's clearing plus dependency order, not by the consumer. Logged residual limitations of this gate (documented, not blocking under the current policy that only V&V-chain test failures are fixed immediately): the consumer cannot prove that the recorded elaboration order is the order actually executed (producer self-attestation); there is no lock against concurrent generator runs, so an interleaved run can abort or produce a transient inconsistency; the `make -j` path is reasoned but not executed end to end; `trace.py` retains a dead branch at lines 209-210; Gitea `@v3` artifact compatibility is unverified; and the synthetic accepted-receipt control is tautological with respect to the validator (it is labelled as a parser control). Synthetic receipts used by the regression suite are parser fixtures and are **not** elaboration evidence.

## Qualification procedure (per tool)

1. The tool/script is placed under configuration management in this repository.
2. Source review for correctness and for traceability to the evidence claims it
   supports (norm N10).
3. If the risk or the class-A target demands it, the review is independent
   (norm N9, profile R2) and recorded in `docs/reviews/`.
4. The tool is exercised in the CI pipeline; a recorded pass is the
   qualification evidence.
5. Any change to a qualified tool/script invalidates its qualification: the
   review is repeated and the register updated in the same commit (norm N11).

**T18 note (build-provenance limitation).** The `frick-rtems-toolchain:local` image
that produced the recorded M10 QEMU pass was assembled by applying the updated
`Dockerfile`'s steps individually (the extra `riscv/rv64imafdc` kernel-bset build
and the `qemu-system-misc`/`cmake`/`ninja-build` install), each executed and
verified in this environment; a single clean `docker build` of the updated
`Dockerfile` was not completed locally. `make rtems-toolchain` provides the clean
image-build procedure, but the base image, apt package resolution, and RSB
reference are mutable; this does not establish bit-for-bit reproducibility.
The recorded image was assembled stepwise, so T18 requalification remains open
pending a clean image build and repeat of `make qemu`/`make renode` under NC-EXT-40.
