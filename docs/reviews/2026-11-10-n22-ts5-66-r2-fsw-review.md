## 2. Architecture and Design Conformance

### 2.1 Coupling Mechanism (src/apps/app_scheduler.c:95–150)

**Design as implemented**:
- **TBL activation callback** (`ff_sched_tbl_activated`, lines 99–116) runs in **command/TBL context** (caller of `FF_TblActivate`).
- Callback **only**: validates handle/image/size match, re-validates image via `FF_SchedValidate`, locks mutex, copies to `g_sched_pending_image`, sets `g_sched_reconfig_pending = true`, unlocks.
- **Scheduler task** applies pending activation at top of its next tick via `ff_sched_apply_pending` (lines 121–150): try-locks mutex (non-blocking), copies pending image, calls `FF_SchedActivate` + `FF_SchedInit`, emits `FF_SCHED_EVT_ACTIVATED` (REACTIVATED_FMT).
- **Single-writer contract preserved**: dispatcher state (`FF_SchedActivate`/`FF_SchedInit`/poll) only touched by scheduler task. Callback never calls into dispatcher or TBL.
- **Deferral bound**: at most one scheduler tick (`FF_SCHED_TICK_MS`). If mutex busy, `ff_sched_apply_pending` returns early and retries next tick.

**Conformance to requirements**:
- ✅ **SRS-REQ-013**: Staged image becomes active only on explicit activate; activation is atomic in dispatcher context.
- ✅ **SRS-REQ-071**: Table validated before activation (TBL load + callback re-validation); activated atomically via double-buffer; heartbeat/missed/publish-failure evidence emitted by scheduler task.
- ✅ **SSS-REQ-030**: Bounded table-driven dispatch; RTEMS task-delay for timing; liveness/overrun reported via EVS.

### 2.2 Real-Time Constraints Assessment

| Constraint | Status | Evidence |

## 3. Findings

### 3.1 Major Findings

#### MAJ-1: Unbounded blocking in TBL activation callback (src/apps/app_scheduler.c:110)
**Location**: `ff_sched_tbl_activated` line 110: `FF_PalMutexLock(g_sched_reconfig_lock, FF_PAL_WAIT_FOREVER)`

**Issue**: The callback uses `FF_PAL_WAIT_FOREVER` when acquiring the reconfiguration mutex. If the scheduler task is preempted while holding the mutex in `ff_sched_apply_pending` (lines 129–137), the callback blocks indefinitely. On a priority-preemptive RTEMS system, this creates a priority inversion window where a medium-priority task could delay the command/TBL context arbitrarily.

**Impact**: Violates "bounded callback" expectation for criticality B. The architecture doc (§5.1 line 160) states "the callback runs in TBL/command context and only validates the image and snapshots it". An unbounded wait contradicts this.

**Required resolution**: 
- Option A: Use `FF_PalMutexTryLock` in callback; if busy, set a flag and return (activation applied on next tick anyway via pending slot — but the slot is only written under the mutex). This requires a lock-free pending slot or a separate callback-status flag.
- Option B: Use a bounded wait with a short timeout (e.g., one scheduler tick budget) and on timeout emit an EVS error and drop the activation.
- Option C: Restructure so callback never blocks (e.g., lock-free atomic pointer swap for pending image, with sequence counter).

**Reference**: ECSS-Q-ST-80C §5.3.2 (bounded execution), ECSS-E-ST-40C §5.4.3 (priority inversion control).

#### MAJ-2: Silent failure when mutex creation fails (src/apps/app_scheduler.c:164–169)
**Location**: `FF_AppSchedulerMain` lines 163–169.

**Issue**: If `FF_PalMutexCreate` fails, `g_sched_reconfig_ready = false`. The table is still registered with the callback (line 174–178). Subsequent TBL activations will enter the callback, hit the `!g_sched_reconfig_ready` guard (line 101), and **silently return** without applying the activation. The TBL layer returns `FF_SUCCESS` (activation callback invoked), but the dispatcher never reconfigures. No EVS event is emitted at activation time to indicate the configuration failure.

**Impact**: Loss of schedule update capability with no ground-visible evidence until a later audit. For Class B, a configuration failure that disables a safety-related function (schedule reconfiguration) must be detectable.

**Required resolution**: 
- Emit an EVS error event at the point of mutex creation failure (already done at line 168).
- Additionally, in the callback, when `!g_sched_reconfig_ready`, emit a `FF_SCHED_EVT_INVALID_TABLE` or dedicated "reconfiguration unavailable" event so that *each* failed activation is visible.
- Consider failing scheduler startup if the reconfiguration lock cannot be created (design decision: is schedule reconfiguration required for mission?).

#### MAJ-3: Callback assumes TBL passes active image pointer; no defense against TBL implementation change (src/apps/app_scheduler.c:101)
**Location**: `ff_sched_tbl_activated` line 101: `(image != &g_sched_image)`

**Issue**: The callback validates that the `image` pointer passed by TBL equals `&g_sched_image`. Per `tbl.c` lines 90–94, TBL copies staged data to `g_tables[h].image` (which is `def->image` = `&g_sched_image`) and then calls the callback with that pointer. The check is currently correct **but** couples the callback to TBL's internal activation sequence. If TBL ever changes to pass the staging buffer pointer, or if a second table registration uses the same callback, this check would silently reject valid activations.

**Required resolution**: 
- Remove the pointer-equality check; rely on `handle != g_sched_tbl` and `size != sizeof(g_sched_image)` which are sufficient to identify the correct table.
- Or, document in `tbl.h` the callback contract that `image` is the **active image buffer** (already stated in `tbl.h` line 26: "newly activated image buffer (which is now the active image)") and treat the pointer check as a defense-in-depth assertion with an EVS event on mismatch.

### 3.2 Minor Findings

#### MIN-1: No EVS event on callback validation failure (src/apps/app_scheduler.c:107–109)
**Location**: `ff_sched_tbl_activated` lines 107–109.

**Issue**: When `FF_SchedValidate(image, size) != FF_SUCCESS`, the callback returns silently. No EVS event, no counter increment in `FF_SchedStats_t` (which has `invalid_activations` but that is incremented only by `FF_SchedActivate` in dispatcher context).

**Impact**: An activation that passes TBL load validation but fails the callback's re-validation (defense in depth) leaves no ground-visible trace. The `invalid_activations` counter in `FF_SchedStats_t` is not incremented because `FF_SchedActivate` is never called.

**Recommendation**: Emit `FF_SCHED_EVT_INVALID_TABLE` (or a dedicated callback-rejection event) and increment a callback-rejection counter (could extend `FF_SchedStats_t` or use a local static).

#### MIN-2: EVS event format coupling in test (tests/unit/test_tbl_sched_coupling.c:352)
**Location**: `test_tbl_sched_production_activate` line 352: `strcmp(evt->text, "SCH: table activated, 2 entries") == 0`

**Issue**: The test asserts the exact format string. This couples the test to the `sched_evt.h` literal. While the format string is a public interface constant (`FF_SCHED_EVT_REACTIVATED_FMT`), the test should reference the constant or at least document the coupling.

**Status**: The format string in `sched_evt.h` line 33 (`"SCH: table activated, %u entries"`) matches the test expectation. No functional defect, but test maintainability note.

#### MIN-3: Double validation (src/apps/app_scheduler.c:105–109)
**Observation**: TBL load already calls `FF_SchedValidate` (registration line 177). Callback re-validates. This is defense in depth (architecture doc §5.1 line 164: "TBL validated the staged image before activation; re-validate the active copy so a corrupt buffer cannot reach the dispatcher"). Acceptable for Class B, but the cost (WCET) should be included in the callback budget (MAJ-1).

### 3.3 Observations (No Action Required)

#### OBS-1: One-tick deferral budget not established (Architecture doc §5.1 line 175, Test Spec N22-TS5-66 Scope limit)
**Status**: Acknowledged open. The deferral is bounded to one scheduler tick, but the WCET of the apply path (`ff_sched_apply_pending` → `FF_SchedActivate` → `FF_SchedInit` → mutex operations) is not measured on target. Mission rates/jitter/tolerances (NC-EXT-19, N22-TS5-48) are TBD. This is correctly recorded as a residual limit, not a gap.

#### OBS-2: Cross-core memory ordering (M14) not established (Architecture doc §5.1 line 139)
**Status**: Acknowledged open. The pending slot uses a mutex which provides acquire/release semantics on a single core. On SMP, the visibility of `g_sched_pending_image` write to the scheduler task's read requires memory barriers or atomic operations. Tracked under M14.

#### OBS-3: Activation→`FF_SchedInit` window not tested (Test Spec §3.1 lines 362–370)
**Status**: Acknowledged test completeness limit. The `ff_sched.h` contract (lines 102–103) states "A new activation clears targets and must be followed by `FF_SchedInit` before dispatch resumes." No host test exercises the window between `FF_SchedActivate` and `FF_SchedInit` (every test calls `FF_SchedInit` immediately). Deferred to next S8-SCH increment.

#### OBS-4: Target/HIL evidence (GAP-A5) and Renode N18 only
**Status**: Correctly recorded. `make renode` passes (N18 emulated PASS), but target silicon (RTPFS160ZT) evidence is GAP-A5. No WCET, jitter, or RTEMS fatal-extension behavior established.

#### OBS-5: Mission-controlled rates/tolerances/recovery authority (NC-EXT-19, N22-TS5-48)
**Status**: Correctly recorded as TBD. SRS-REQ-071 and SSS-REQ-030 explicitly state these are mission-controlled inputs. No flight-use authorization implied.

## 5. Overall Disposition

### APPROVED WITH COMMENTS

**Rationale**: The N22-TS5-66 delta correctly implements the Table Services load/activate → scheduler dispatch coupling with:
- Proper separation of TBL callback (snapshot only) and dispatcher task (apply)
- Single-writer dispatcher contract preserved
- Atomic activation via `FF_SchedActivate` + `FF_SchedInit` in dispatcher context
- Bounded one-tick deferral (architecturally, though WCET unmeasured)
- Nominal + OOB test coverage with explicit oracles per N22
- Traceability to SRS-REQ-013, SRS-REQ-071, SSS-REQ-030 and ECSS Class B expectations

**The three Major findings (MAJ-1, MAJ-2, MAJ-3) must be resolved before sprint closure** (AGENTS.md N15). They affect:
- Bounded execution guarantee (MAJ-1) — critical for real-time Class B
- Silent configuration failure (MAJ-2) — observability requirement
- Coupling to TBL implementation detail (MAJ-3) — maintainability/robustness

**Minor findings (MIN-1, MIN-2) are recommendations** for improved diagnostics and test maintainability.

**Open items (OBS-1…5) are correctly acknowledged** and do not block this delta's approval; they remain tracked under their respective NCs/GAPs.
