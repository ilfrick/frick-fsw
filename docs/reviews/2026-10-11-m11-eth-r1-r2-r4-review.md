## 1. Scope

Reviewed the fourth M11 HAL-coverage increment: **ETH (Cadence GEM) exercised
on the emulated PolarFire SoC** by identifying the emulated MAC through its
read-only Module ID/revision register.

- **R1 (design/code)**: correctness of `ff_gem_*`-independent MMIO probe
  `renode_hal_eth_check` (`app_renode_test.c:103-117`) and the constants
  `FF_GEM0_BASE`/`FF_GEM_MODID_OFF` (`platform_mpfs.h:37-38`) against the pinned
  Renode `CadenceGEM` model (`Registers.ModuleId`, field layout, read-only
  semantics), the `polarfire-soc.repl` mapping, and the Cadence GEM / MPFS MSS
  register map.
- **R2 (V&V)**: marker AND logic, validity and strength of the check as
  requirement evidence (SRS-REQ-036), and reproducibility of the recorded gates
  (`make renode`, native `ctest`, `trace.py`).
- **R4 (documentation, N17)**: consistency of the changed docs
  (`traceability.yaml`, `verification-results.md`, `handover.md`, `loop-audit.md`,
  `CHANGELOG.md`) with the code and with the unchanged documents that also
  describe the Renode test (`docs/vv/renode-environment.md`,
  `docs/requirements/traceability.md`); counts/revisions/history; over-claim.

Excluded: real-silicon GEM DMA/link/PHY behaviour (GAP-A5); MISRA/WCET runtime
evidence (GAP-A4).

### Empirical evidence

**Correctness (R1) — independently verified, not read from the change.**

- Model (`CadenceGEM.cs`, pinned v1.16.1): register enum `ModuleId = 0xFC`
  (line 1147); register fields — `WithValueField(0, 16, FieldMode.Read,
  "module_revision")`, `WithValueField(16, 12, FieldMode.Read,
  "module_identification_number")`, `WithTag("fix_number", 28, 4)`. Constructor
  defaults `moduleRevision = 0x118`, `moduleId = 0x2` (lines 31-34). So
  `[15:0]` = revision, `[27:16]` = identification, all `FieldMode.Read` — exactly
  what the code and its comment (`app_renode_test.c:115`) state.
- Platform mapping: `polarfire-soc.repl:116`
  `mac0: Network.CadenceGEM @ { sysbus 0x20110000; sysbus 0x28110000 }` — `mac0`
  is at `0x20110000`, matching `FF_GEM0_BASE`. `CadenceGEM.Size = 0x1000`, so
  `0xFC` is in range.
- Datasheet: Cadence GEM register map `0x0FC Module ID RO 0x0002_xxxx`; Xilinx
  `macb.h` `MACB_MID 0x00fc`. Offset and reset-shaped value agree with the model.
- Live probe of the emulated device (Renode telnet monitor, pinned image):
  - `sysbus ReadDoubleWord 0x201100FC` → `0x00020118` (id `0x0002`, rev `0x0118`);
  - `sysbus WriteDoubleWord 0x201100FC 0x0` then re-read → still `0x00020118`
    (register is read-only → the check cannot corrupt the model);
  - `sysbus ReadDoubleWord 0x20110000` → `0x00000000` (NetworkControl reset; the
    peripheral is genuinely mapped); `0x202000FC` → `Unhandled read` warning (an
    unmapped/wrong window returns 0). The check therefore distinguishes a mapped
    GEM from an unmapped region — it is **not vacuous**.
- The app reads only (no writes anywhere), and the value satisfies the predicate
  `modid != 0 && ((modid>>16)&0xFFF) != 0 && (modid&0xFFFF) != 0` → PASS.

## 4. Conclusion

- **R1 (design/code)**: **APPROVED WITH COMMENTS**. The identification is
  technically correct: `Registers.ModuleId` is at `0xFC`, fields are
  `[15:0]` revision / `[27:16]` identification, the register is read-only (write
  ignored; verified live), and `mac0` is at `0x20110000`. The check is meaningful
  (distinguishes mapped GEM from an unmapped window) and non-corrupting. However,
  it does not exercise the ETH HAL/driver (R1-01, Minor) and the oracle only
  tests non-zero (R1-02, Comment).
- **R2 (V&V)**: **APPROVED WITH COMMENTS**. Both gates reproduce independently:
  `make renode` → `[renode] PASS` with `hal_eth=PASS`, and native `ctest` 14/14;
  the marker logic is correct and `trace.py` converges. `make renode` required a
  `chown` of the container-built `build/renode` (R2-01, Minor; pre-existing
  tooling), the documented toolchain-image path was stale on this host (R2-02,
  Comment), and the `ci:renode` claim is applied inconsistently across the M11
  classes (R2-03, Comment).
- **R4 (documentation, N17)**: **APPROVED WITH COMMENTS**. The CHANGELOG and the
  `verification-results.md` row are accurate and well-scoped, but the change left
  two documents that describe the same functionality stale — `renode-environment.md`
  (R4-01, Minor) and `traceability.md` (R4-02, Minor) — and did not bump the
  `handover.md` revision/History (R4-03, Minor, N16); plus the recurring header
  comment (R4-04), loop-audit currency (R4-05), trailing-newline (R4-06) and
  review-log (R4-07) items.

**Overall**: **APPROVED WITH COMMENTS** — no Major findings. The increment is a
correct, independently reproduced GEM identification check; the identification
constants and the register semantics are accurate and non-corrupting. The Minor
findings — ETH framed as a HAL "class" while only the MMIO window is probed, the
untouched `renode-environment.md` and `traceability.md`, the missing handover
history entry, and `make renode` reproducibility — must be corrected or
justified and tracked to closure (norm N12) before the change is considered
closed.
