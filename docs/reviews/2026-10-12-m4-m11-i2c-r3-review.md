## 3. Findings

### 3.1 Verification of the item under review

**Fact - SRS-REQ-058 is truthful and testable for the delivered behaviour.**
The requirement (`SRS.md:304-319`) states: a reference HAL I2C backend for the
MSS I2C (CoreI2C), `FF_I2c_t`, **polled master** with `init`/`write`/`read`/
`write_read`; injected **byte-addressed MMIO** bus; register-based and
allocation-free; `init(clock_hz)` selects the serial-clock divider; bounded SI
poll; the divider is a **reference derivation** from the APB clock with per-rate
accuracy tracked as **GAP-A5**; the **minimum achievable SCL** is `PCLK/960`
(~104.17 kHz at the 100 MHz reference) and a request below it is **not honoured**
(caller must request >= that minimum); polled-master-only limitations (7-bit
addressing; no slave/SMBus/clock-stretching/bus-recovery/STOP-completion/interrupt
path); **not re-entrant** (caller must serialise). I verified each clause against
the source: the four methods and the byte MMIO bus are exactly `FF_I2c_t` /
`FF_I2cBus_t` (`hal_spi.h:27-36`; `ff_i2c_mpfs.h:89-94`); the divider selection
is `i2c_pick_div` (`ff_i2c_mpfs.c:70-81`); the bounded poll is `FF_I2C_POLL_MAX`
(`ff_i2c_mpfs.h:133-136`, `ff_i2c_mpfs.c:84-95`); `FF_I2C_MIN_SCL_HZ =
FF_I2C_MPFS_CLK_HZ/960` (`ff_i2c_mpfs.h:146-151`); the limitations match
`ff_i2c_mpfs.h:46-74`; no allocation is used (static instance only,
`ff_i2c_mpfs.c:22`). The claim "not honoured" is accurate: `i2c_pick_div`
returns the slowest divider when no divider fits and `i2c_init` still returns
`FF_SUCCESS` (`ff_i2c_mpfs.c:65-69,116-128`). **Inference (High):** the
requirement does not over-claim.

**Fact - the backend conforms to the `FF_I2c_t` contract.** `FF_I2cMpfs_t` embeds
`FF_I2c_t i2c` **first** (`ff_i2c_mpfs.h:172-178`), and `FF_I2cMpfsSetup`
completes the vtable with `name`, `init`, `write`, `read`, `write_read`
(`ff_i2c_mpfs.c:344-359`) using signatures identical to `hal_spi.h:27-36`. There
are no extra or missing members. The one contract-level constraint - the contract
carries **no per-instance context**, so a single static instance is bound
(`g_i2c`, `ff_i2c_mpfs.c:22`; documented at `ff_i2c_mpfs.h:72-74`) - is a
property of the contract, not a conformance defect.

**Fact - parenting and traceability are coherent.** `traceability.yaml` gives
**SRS-REQ-058** `parent_sss: SSS-REQ-020` (`:543-550`), and SSS-REQ-020 is
"*Reference low-level implementations ... reference implementations of the HAL
contracts for the target platform*" (`SSS.md:89-92`) - a correct parent for a
reference HAL backend. **SRS-REQ-031** remains the contract requirement
("*SPI, I2C, PCIe and GPIO ... contracts*", `SRS.md:140-142`) with
`parent_sss: SSS-REQ-017` (`traceability.yaml:298-305`), implemented by
`hal_spi.h`/`hal_pcie.h`/`hal_gpio.h`, and SSS-REQ-017 is the HAL contract
requirement (`SSS.md:73-79`). The `FF_I2c_t` contract therefore traces to the
contract requirement (SRS-REQ-031/SSS-REQ-017), and the reference backend to
SRS-REQ-058/SSS-REQ-020 - the two are consistently separated. **Fact:** SSS.md is
**not modified** by this increment (SSS-REQ-020 is pre-existing), so the N14
trigger is the parenting coherence checked here rather than a change to the SSS
text; the parenting is coherent.

**Fact - interface / scope statements are consistent and do not over-claim.**
`ICD.md:15-19` states that board-level peripheral interfaces and their
register/address maps are **not** part of the TM/TC ICD (they live in the
HAL/driver headers and platform headers) - this correctly removes the I2C
contract/register map from the TM/TC ICD scope (prior finding R3-06).
`software-design.md:113` allocates SRS-REQ-058 to the reference-driver design
element; `network-stack.md` does not touch I2C (correctly out of scope). The
Renode check is honestly scoped: `renode-environment.md:111-118` states the
emulated `I2C.MPFS_I2C` does not model the CTRL CR0/CR1/CR2 divider bits and
advances on register writes, so the check asserts ENS1 + IDLE + the ADDR/
SLAVE1_ADDR round trip only, with the full transaction path host-tested -
consistent with `app_renode_test.c:266-295` and with SRS-REQ-058's "emulated-MMIO
register check" wording (not an emulated transaction claim).

**Summary judgement.** SRS-REQ-058 describes the delivered behaviour truthfully
and testably, with the exceptions noted as new findings R3-10…R3-12 (wording
precision / completeness, not falsehood); the backend conforms to `FF_I2c_t`;
the parenting is coherent; the interface/scope statements are consistent and
free of over-claim. The increment has **no Major** systems/requirements/interface
finding. One **Minor** traceability-consistency finding (R3-09) and four
**Comment** findings (R3-10…R3-14) are recorded.
