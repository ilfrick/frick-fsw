## 2. Findings

### B-01 (Blocker) — the six Lean theorems were not elaborated and did not compile

`verification/lean/Frick/Watchdog.lean` was **not import-reachable**: nothing imports `Frick.Watchdog`;
`Frick/Requirements.lean` did not import it; the default `lake build` target builds `Main`, which imports
only `Frick.Requirements`/`Frick.Ccsds`. The tracked `lake-build.log` enumerates 21 steps with no
`Frick.Watchdog`. A `lake build` in the pinned Lean 4.10.0 image produced **no `Watchdog.olean`**, and once
the module was made reachable it **failed to compile** — `req_srs074_report_precedes_reset` used
`List.idxOf` and `req_srs075_one_reset_action` used `List.count`, neither present in Lean 4.10 core.

**Impact.** The N1/N3 "every generated requirement is verified in Lean" gate was not actually satisfied for
the six SRS-REQ-073/074/075 theorems, while `make trace` (regex scan) and `lake build` both passed.

**Disposition (recorded):** corrected under N21 — `Frick/Requirements.lean` imports `Frick.Watchdog`, and
the two theorems were re-expressed with core `List` operations; theorem names unchanged. A `lake build` in
Lean 4.10.0 now compiles the module (25 steps, `Watchdog.olean`, "Build completed successfully"). Registered
as **NC-EXT-120** (Major functional/verification), OPEN pending independent R2/R3 re-review under N12.

### M-01 (Major) — "exactly one pre-reset report" has no emission-count oracle

TS-5 `N22-TS5-50`/`N22-TS5-80` claim "exactly one" report, but the oracle `hs_reset_writer`
(`tests/unit/test_es_hs_lifecycle.c:341-349`) copies into a single buffer and does not count invocations
(only `g_reset_frame_len > 0u` and `frame_contains` are asserted). A duplicate emission would still pass.
**Action:** add an emission counter and assert `count == 1`.

### M-02 (Major) — SRS-REQ-073 feed-margin and arming-order clauses lack objective evidence

SRS-REQ-073 requires feeding at "≤ timeout/4" and a specific arming order (install reporter, then arm).
The derivation is `src/apps/app_wd.c:42-43`/`FF_WD_FEED_DIVISOR 4u` (`app_wd.c:29`); no unit/integration test
exercises `FF_AppWdMain`, the divisor, or the arming order, yet `traceability.yaml` lists
`test_pal_watchdog.c` as evidence for SRS-REQ-073. **Action:** add coverage or record a bounded analysis and
narrow the `tests:` list (requirements authority owns acceptance).

### M-03 (Major) — "within a bounded worst-case time" (SRS-REQ-074) is not objectively testable

`docs/requirements/SRS.md:438` says "within a bounded worst-case time"; the SRS-REQ-074 `lean_note` concedes
the worst-case bound is **not established**. No numeric bound or method exists to verify/falsify the clause.
**Action:** quantify the bound with an analysis/measurement method, or move the clause outside the
V&V-verifiable set (requirements authority).

### M-04 (Minor) — erroneous test attribution for SRS-REQ-074

`traceability.yaml` SRS-REQ-074 `tests:` includes `tests/unit/test_pal_watchdog.c`, which never installs a
panic notifier and cannot observe the PUS S5 report. **Action:** remove it or add the specific assertion.

### M-05 (Minor) — `req_srs075_single_reset_path` is `rfl` on two identical aliases

`Watchdog.lean:89-99`: `commandedReset` and `watchdogTimeout` are both `recoverySequence`, so the theorem is
trivially true and does not model that the C realises one shared path. **Action:** give the paths distinct
abstract definitions and prove they yield the same recovery list, or relabel as an alias lemma.

### M-06 (Minor) — boundary test has a 1 ms jitter margin on a shared host clock

`tests/unit/test_pal_watchdog.c:76-82` starves 999 ms (expect `FF_SUCCESS`) and 1001 ms (expect
`FF_TIMEOUT`) against a 1000 ms limit; host jitter > 1 ms can flip the 999 ms case. **Action:** widen the
margin or inject a clock.

### m-01 (Minor) — truncated-command OOB case does not assert "no report"

`tests/unit/test_es_hs_lifecycle.c:478-506` asserts `!g_panic_seen` and no reset increase but never checks
`g_reset_frame_len` (unlike the sibling at `:458`/`:470`). **Action:** set/assert `g_reset_frame_len == 0`.

### m-02 (Minor) — no test for the "notifier unset (NULL)" case

`FF_PalPanic` guards `if (g_panic_notifier != NULL)` (`pal_posix.c:571-573`); the only failure-path test uses
a *failing* reporter, not a NULL/unset notifier, while TS-5 `N22-TS5-80` claims "notifier-unavailable".
**Action:** add a NULL-notifier case or reword the claim.

### C-01 (Comment, non-functional) — `FF_PalWatchdogCheck` is flight-dead code with a contradictory header

`pal.h:92-95` says the check lets the feeder detect a missed deadline, but `app_wd.c:55-58` calls only
`FF_PalWatchdogFeed()`. **Action:** wire it or correct the comment (NC, non-blocking under N21).

### C-02 (Comment, safety-relevant — escalate) — init cannot detect an unwired hardware binding

`pal_watchdog.c:52` discards `ff_pal_wd_hw_arm`'s return; `FF_PalWatchdogInit` returns `FF_SUCCESS`
unconditionally, and the RTEMS hooks return `FF_NOT_IMPLEMENTED` (`pal_rtems.c:73-88`). On target the
software proceeds as if protection exists. Already tracked as **NC-PAL-01**; flagged for authorized-human
sign-off. No safety conclusion is drawn here.
