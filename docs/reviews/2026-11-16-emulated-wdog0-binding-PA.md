## 1. Scope

**Reviewed:**
- The emulated MPFS MSS WDOG0 binding implemented in `src/core/pal/pal_rtems.c` under `FRICK_PLATFORM_MPFS && FF_ENABLE_RENODE_TEST`, using the pinned Renode model's 156,250 Hz clock (FF_WDOG_EMU_CLK_HZ), MSVP=TIME, TRIGGER=4095, register order TRIGGER→MSVP→TIME→CONTROL with read-back before first REFRESH.
- The portable watchdog state machine in `src/core/pal/pal_watchdog.c` and its simulated backend in `src/core/pal/pal_posix.c`.
- The `FF_PalPanic` rework: log → lock-free pre-reset PUS S5 event report (single absolute-monotonic 250 ms deadline) → single reset path (`FF_PalWatchdogReset`) → test seam → `abort()`.
- The watchdog feeder app (`src/apps/app_wd.c`) using absolute monotonic deadlines (`FF_PalTaskDelayUntilNs`) to avoid cumulative drift.
- Lean 4 theorems in `verification/lean/Frick/Watchdog.lean` (6 theorems modelling software-visible arm/feed/expiry, report-before-reset ordering, single reset path).
- Unit test suites: `tests/unit/test_pal_watchdog.c` (11 cases, 320 checks) and `tests/unit/test_es_hs_lifecycle.c` (14 cases, 22 reset-path checks).
- All associated documentation: ADR-0021, architecture spec, sprint-plan, handover, loop-audit, verification-results, traceability.

**Excluded:**
- Flight-target MPFS MSS watchdog hardware binding (explicitly NOT IMPLEMENTED per NC-PAL-01).
- Target/HIL evidence (GAP-A5 open).
- External watchdog (XW2) target contract evidence (PIL-QEMU only).
- Schedulability, jitter, WCET claims (no controlled inputs).

| 1 | **Blocker** | SRS-REQ-074 / ECSS-E-ST-70-11 5.7.5.2 / N20 | **Pre-reset report path is not demonstrably bounded on the flight target, and the reset may not proceed if the notification fails.** The host `FF_PalPanic` path (pal_posix.c:568-632) calls `fprintf/fflush(stderr)` → notifier → `FF_PalWatchdogReset` → `abort()`. The flight notifier is `FF_LinkSendUntil` (fsw_main.c:98), which on RTEMS reaches the UART link's blocking `write()` on a blocking descriptor (link_uart.c:88, 107-112). A panicking task can block in stdio or in `write()` and never reach `FF_PalWatchdogReset()`, contradicting SRS-REQ-074 ("failure or absence of that notification shall not prevent the reset from being enforced") and ADR-0021. `FF_PusNextTmCounter()` is also a non-atomic read-modify-write on this path. This is a **SAFETY-RELEVANT BLOCKER** (NC-EXT-168) escalated to the authorized human owner. The emulated N18 run does not exercise this path (the emulated binding uses the loopback writer, not UART). | `pal_posix.c:568-632`, `link_uart.c:88-112`, `fsw_main.c:98`, `traceability.yaml:711-750` (lean_note: "Report-before-reset ordering remains established by inspection and the Lean theorem... not the simulated backend"), `sprint-plan.md` NC-EXT-168 (Blocker). | **Owner decision required.** Options: (a) Bound the write (non-blocking or timeout-bounded) and drop/defer the stdio log on the flight path; (b) Drive the reset from a path independent of the writer (e.g., direct hardware reset from a separate task/ISR); (c) Explicitly accept the residual risk and correct the code comment to stop claiming boundedness.
