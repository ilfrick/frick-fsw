## 3. Findings

### Finding 1 — ES/HS heartbeat oracle coupled to implementation literal (Minor; Question a/d)
**File:** `tests/unit/test_es_hs_lifecycle.c:178, 180–185`  
**Evidence:** `FF_TEST_ASSERT(cap_count_id(0x0502u) == 2u);` hardcodes heartbeat event id; the production implementation emits `0x0502u` at `src/apps/app_hs.c:55` and no symbolic constant is defined in headers. Also the "FAILED application" identification relies on matching `"HS: app %u failed"` text in the event string (`cap_hs_reports` at lines 86–100), while the EVS event’s `app_id` field is the HS app id (not the failed app id).  

**Issue:** The expected heartbeat id and the text-based extraction of the failed app id are derived from the implementation being tested (same literal and same message format). This introduces coupling between oracle and implementation (a form of common-mode dependency) even though the EVS listener seam itself is independent. The test’s disclaimers (lines 16–22, 227–231) explicitly state scope and non-closure of GAP-R3-1, but do not explicitly call out the literal/text coupling as an independence limitation.

**Severity:** Minor  
**Recommendation:** Add a brief note in the test header or associated documentation that the heartbeat id and the diagnostic message text are implementation-defined by `app_hs.c` (not fixed by a controlled requirement clause); if independence must be strictly demonstrated, define a controlled identifier/text contract or use a symbolic constant exposed by a controlled header. The current explicit disclaimers mitigate impact for this bounded host evidence.

### Finding 2 — CRC-consistency check in decoder corpus is not independent (Minor; Question a,e)
**File:** `tests/unit/test_decoder_corpus.c:140–148, 344–356`  
**Evidence:** Working-tree delta changes the comment to clarify `crc_matches()` uses `FF_CcsdsCrc16` (same routine as the decoder) and the verdict-consistency check for `FF_CRC_ERROR` is not independent.  

**Issue:** The oracle for “CRC mismatch detected” includes an internal consistency check that shares the CRC implementation with the decoder. This cannot detect a common-mode defect in `FF_CcsdsCrc16`. The revised comment is accurate and honest. However, the test does not record this limitation in the “oracle ground” section of the test spec; TS-1/TS-6 oracles treat SRS-REQ-004 as satisfied by the observed decoder behavior and by the CRC property tests in the Lean/codec suite.

**Severity:** Minor  
**Recommendation:** Update the relevant test-spec case text (TS-1/TS-6 entries referencing the corpus CRC checks) to state this limitation explicitly (common-mode in the shared CRC routine) so readers do not infer independent CRC cross-checking. The code comment already does this; mirror in specification language.

### Finding 3 — N7 adapter test claims “independent reference cross-check” but uses shared CRC (Minor; Question c,e)
**File:** `tests/unit/test_pus_n7_adapter.c:116–124`  
**Evidence:** The comment states “Independent reference cross-check of bytes emitted by the generated N7 CRC routine…” but the check compares against `FF_CcsdsCrc16(frame, len-2)` (line 120). The cross-check is N7 encoder vs reference decoder’s CRC routine, not an independent CRC implementation; both rely on the same project CRC semantics in this assertion.

**Issue:** The comment overstates independence. The actual verification is: (a) N7 backend encodes TM using generated N7/ESA CRC wrapper; (b) the encoded frame’s trailer equals the reference `FF_CcsdsCrc16` of the covered region; (c) `FF_CcsdsDecodeTm` decodes successfully. The CRC equality is a compatibility/oracle check, not independence of implementations. The test’s substantive oracles (TC CRC rejection on corruption, structural boundary/type checks, NULL header rejection) remain valid.

**Severity:** Minor  
**Recommendation:** Rephrase the comment to avoid “independent reference cross-check” (e.g., “CRC trailer compatibility check against the reference codec’s CRC routine”). No functional change required.
