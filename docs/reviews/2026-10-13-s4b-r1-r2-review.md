| **R1-01** | **Major** | SRS-REQ-059 — TCP reassembly | **Partial-read recovery discards buffered state, causing stream desync.** In `FF_LinkSegRecvFrame`, Phase 4 reads the frame payload directly into the caller's `frame` buffer (not into `rx_partial`). When `read_bytes` returns 0 mid-payload (line 115–119), the code sets `seg->rx_len = 0u` and returns `*len = total` with `FF_TIMEOUT`. The comment on line 116 says "keep what we have in rx_partial for next call" but the code does the **opposite** — it wipes `rx_partial` and discards the 2-byte length prefix + any partial payload. On the next call, the remaining bytes in the TCP stream (belonging to the current frame) are read as a **new length prefix**, decoded as a garbage frame length, and the stream is desynchronised. This defeats the core purpose of the seg layer: reliable frame reconstruction over TCP streams. | `link_seg.c:100–127` (Phase 4); comment contradicts code at `:116–117`; `g_tcp_rx` not involved | Restructure Phase 4 to buffer partial payload into `rx_partial` (copy `frame[0..total-1]` back to `rx_partial[FF_LINK_SEG_PREFIX_LEN..]` and set `rx_len = FF_LINK_SEG_PREFIX_LEN + total` before returning `FF_TIMEOUT`), so the next call resumes correctly. Add a fragmented-stream test that drives the seg layer with a mock returning 1 byte per call. |
| **R1-02** | **Major** | SRS-REQ-061 — TSN RX callback ISR safety | **A blocking mutex is taken from the MAC RX callback, which fires from ISR context on real hardware.** `tsn_eth_rx_cb` (line 56) calls `FF_PalMutexLock(g_lock, FF_PAL_WAIT_FOREVER)`. On the real Cadence GEM / Microchip PolarFire SoC, the MAC delivers received frames via an interrupt service routine, which invokes `set_rx_callback`'s callback. `FF_PalMutexLock` wraps `pthread_mutex_lock` with `FF_PAL_WAIT_FOREVER` (`pal_posix.c:247–248`), which blocks indefinitely. Calling a blocking mutex lock from an ISR is unsafe on RTEMS POSIX (the underlying `pthread_mutex_lock` from ISR context returns an error rather than blocking). **Worse, the return value is not checked** (line 56), so on an ISR the lock silently fails and the ring-buffer head/tail/count fields are read and written without any synchronization — a data race that can corrupt the RX ring and deliver garbage CCSDS frames to PUS-C. No test exercises ISR context (the mock calls `simulate_rx` from a normal task). | `link_tsn.c:56` (callback entry, lock with no return check); `link_tsn.c:36–64` (callback body); `pal_posix.c:241–256` (mutex lock impl) | Use an ISR-safe critical section (interrupt disable/restore or a dedicated ISR-safe ring buffer) instead of a blocking mutex. At minimum, check the `FF_PalMutexLock` return value and handle failure. Document the delivery-context assumption (ISR vs task) in the header. Add a note under GAP-A5. |

## 4. Conclusion

- [ ] APPROVED — no findings or Comments only
- [ ] APPROVED WITH COMMENTS — Minor findings tracked to closure
- [x] **REJECTED** — two Major findings (R1-01, R1-02) open

The S4b increment is **architecturally well-structured**: the `FF_Link_t` vtable dispatch, the static-global state model, the separation of prefix/framed payload handling, and the Ethernet frame construction all follow the project's no-dynamic-allocation discipline (SRS-REQ-015) and the documented `FF_Link_t` contract. The code is clang-format clean, the requirement chain is traced, and the 27 ctest checks pass.

However, two **Major** defects were identified that, per norm N12, block commit/push until resolved:

1. **R1-01 (Major):** The seg layer's TCP reassembly destroys partial state on mid-frame timeout, causing **protocol desync and frame corruption** on any TCP stream that delivers data in fragments. The comment on line 116 explicitly contradicts the code (`rx_len = 0u` discards the prefix and partial payload that the comment claims to "keep"). The entire purpose of SRS-REQ-059 — "segmentation and reassembly of PUS-C/CCSDS frames for stream-oriented links (TCP)" — is defeated. No test exercises this path because the mock `read_bytes` always returns all available data at once.

2. **R1-02 (Major):** The TSN RX callback takes a **blocking mutex (`WAIT_FOREVER`) from what is ISR context on real hardware**, and the return value is not checked. On RTEMS POSIX, `pthread_mutex_lock` from an ISR returns an error; the unchecked failure leaves the RX ring buffer unprotected, risking **data corruption** that could deliver garbage CCSDS frames to PUS-C. This is a real-time safety and ECSS Class B concern. No test exercises ISR context.

Both defects have zero coverage in the existing test suite and cannot be detected by the current mock-based tests. The fixes are bounded and well-understood (see recommendations), but the deltas must be re-reviewed (norm N12) before commit/push.

## 8. FSW / V&V review questions

**Q1 — Seg-layer buffer safety (link_seg.c).** All array accesses in Phase 1 (`rx_partial[seg->rx_len + i]` where `i < got <= room = 2 - rx_len`, so `rx_len + i < 2 <= sizeof(rx_partial)`) and Phase 3/4 (`memcpy` bounded by checked `frame_len <= cap`) are within bounds. No overflow. ✓

**Q2 — Protocol correctness of reassembly.** **Defective.** See R1-01. The `got == 0` path in Phase 4 (lines 115–119) sets `rx_len = 0`, discarding the length prefix and any partial payload that the next call must reconstruct. The comment contradicts the code. Without preservation, the stream desyncs.

**Q3 — TCP vs UDP dispatch.** `ip_send`/`ip_recv` correctly branch on `g_cfg.mode`: TCP → seg layer, UDP → direct send/recv. ✓

**Q4 — Static-global state model.** All backends use static globals (no context pointer in `FF_Link_t` vtable). No dynamic allocation anywhere. ✓ Consistent with SRS-REQ-015.

**Q5 — TSN RX callback race / ISR safety.** **Defective.** See R1-02 (blocking mutex in ISR) and R1-03 (TOCTOU). The ring-buffer indices (`g_rx_head`, `g_rx_tail`, `g_rx_count`) are mutated under `g_lock` in `tsn_link_recv` and in `tsn_eth_rx_cb`, but the lock is blocking and not ISR-safe, and is checked inconsistently (R1-03).

**Q6 — TSN frame construction.** Dest MAC, src MAC, EtherType (BE 0x88F5), payload, pad to 60 bytes — all correct. ✓ No VLAN tag insertion (R1-13, Comment).

**Q7 — IP init / accept semantics.** `ip_init_tcp` calls `listen(1)` then `accept()` (blocking, R1-07). `ip_init_udp` binds and (non-fatally) connects. ✓ structurally but blocking accept and silent fallback are design concerns (R1-07, R1-08).

**Q8 — Test discrimination.** The mocks are behavioural fakes (as declared in their headers). They cannot discriminate R1-01 (the seg-layer desync) because `mock_read` always returns all data at once — the `got == 0` path is never exercised. They cannot discriminate R1-02 because `simulate_rx` runs in task context, not ISR. This is the root V&V gap.

**Q9 — Traceability and Lean (N1/N4).** Traceability passes (SRS-REQ-059/060/061 → source + tests). Lean theorems are `lean: []` with documented `lean_note` justifications — no formal model is claimed for these reference backends. This is correctly recorded (no silent waiver).

**Q10 — Error-code discipline.** See R1-10 (TCP `FF_BUFFER_FULL` vs UDP `FF_ERROR` for partial send) and R1-11 (unchecked mutex returns).

## Facts, Assumptions, Inferences, Recommendations, Confidence, Open gaps

**Facts** (verified first-hand, this session)

- `FF_LinkSegRecvFrame` Phase 4 (lines 100–127) reads the payload directly into the caller's `frame` buffer, not into `rx_partial`.
- At line 117, `seg->rx_len = 0u` discards the 2-byte prefix and any partial state; the comment at line 116 says "keep what we have in rx_partial for next call" — the code and comment disagree.
- `tsn_eth_rx_cb` (line 36) is registered as the MAC RX callback (line 107) and calls `FF_PalMutexLock(g_lock, FF_PAL_WAIT_FOREVER)` at line 56 with no return-value check.
- `FF_PalMutexLock` wraps `pthread_mutex_lock` (pal_posix.c:248) which is not ISR-safe on RTEMS POSIX.
- `g_rx_count` is read unsynchronized at line 41 before the lock at line 56.
- `g_tcp_rx` / `g_tcp_rx_len` (link_ip.c:26–27) are initialized at lines 142–143 and never read.
- `FF_LINK_IP_MAX_FRAME` (link_ip.c:21) is defined and never referenced in the codebase.
- `tsn_link_send` allocates `uint8_t frame[1038]` on the stack (line 170).
- The mock `read_bytes` (test_link_ip.c:43–56) returns all available data in one call; it never returns partial data or 0 with `FF_SUCCESS`.
- The mock `net_send` (test_link_ip.c:131–144) always sets `*sent = len`; it never returns a partial send.
- Traceability: SRS-REQ-059 → `link_seg.{c,h}`; SRS-REQ-060 → `link_ip.{c,h}`; SRS-REQ-061 → `link_tsn.{c,h}` (`traceability.yaml:552–577`). All have `lean: []` with documented `lean_note`.
- ctest: 27/27 PASS (S4b row in `verification-results.md`). Renode: SKIP (host-only code).

**Inferences**

- Because Phase 4 discards `rx_partial` and the mock never returns partial data, R1-01 is untested by construction — the test suite cannot detect it.
- Because the TSN RX callback uses a blocking mutex that is not ISR-safe, the reference backend cannot be safely deployed on the target without modification or explicit documentation that the MAC driver delivers callbacks from task context.
- The `FF_BufferFull` return on partial TCP write (link_ip.c:40) combined with no retry logic in the seg layer means a partial write causes the entire frame send to fail — acceptable but should be consistent with the UDP path error code (R1-10).
- The dead `g_tcp_rx`/`g_tcp_rx_len` and dead `FF_LINK_IP_MAX_FRAME` indicate the TCP receive path was partially refactored and leftover state remains — suggesting the code may not have been reviewed for dead-code elimination alongside the seg-layer integration.
