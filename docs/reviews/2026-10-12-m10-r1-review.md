## 1. Scope

Fold this increment into M10: the Renode leg was already reviewed
(`FRICK-REVIEW-0035`); this review covers only the new **QEMU leg** and its
supporting changes:

- `cmake/toolchains/rtems-riscv-generic.cmake` (new, generic
  `riscv/rv64imafdc` BSP toolchain file) - BSP root/include/lib paths, flags,
  and whether MPFS assumptions leak;
- `tools/scripts/qemu_vv.sh` (new, tool **T20**) - correctness, robustness,
  SKIP/FAIL semantics, hang-bounding, exit codes, marker choice, console
  retention;
- `Makefile` targets `qemu-image`, `qemu-image-docker`, `qemu`; `.PHONY` update;
- the `tools/scripts/emulated_run.sh` QEMU-leg change (prefer the toolchain
  image; host fallback);
- the `tools/docker/rtems/Dockerfile` change (extra `rv64imafdc` BSP build +
  `qemu-system-misc cmake ninja-build`);
- the claims attached to the recorded `make qemu` PASS in the V&V docs and
  evidence registers.

**Out of scope / not verified here:** the Renode leg (covered by
`FRICK-REVIEW-0035`), the actual `docker build` and `make qemu` executions
(unavailable/host-prohibited), the flight `mpfs64imafdc` image, real silicon.

### What was verified as correct (positive evidence)

- **Frozen baseline integrity**: all five frozen files match the declared
  sha256 (see §1 table); no tracked file other than this report was modified.
- **Toolchain file** (`rtems-riscv-generic.cmake`): BSP root
  `${RTEMS_HOME}/6/riscv-rtems6/rv64imafdc`, include `.../lib/include`, lib
  `-L.../lib -qrtems`; `-march=rv64imafdc -mabi=lp64d -mcmodel=medany`
  (the medany multilib the generic BSP uses). It is a faithful generic
  counterpart of the flight `rtems-riscv-mpfs.cmake` and contains **no MPFS
  assumptions** (the leak is in `CMakeLists.txt`/config, not here) - see R1-01.
- **Generic build is genuine at the BSP level**: `build/rtems-generic/build.ninja`
  references only `riscv-rtems6/rv64imafdc`; no `mpfs64imafdc` BSP path.
- **ELF**: `readelf -h build/rtems-generic/frick_fsw` = ELF64, machine RISC-V,
  `EXEC`, double-float ABI, entry `0x80000000` - consistent with the QEMU
  `virt` RAM base and the claimed `-bios` boot.
- **`qemu_vv.sh` robustness**: `bash -n` clean; `set -uo pipefail`; the QEMU
  process is always bounded by `timeout` (20 s) so the script cannot hang;
  exit codes are coherent (SKIP=0, PASS=0, present-but-no-banner=1); the AND of
  `frick-fsw` **and** `applications registered` correctly requires the program
  to reach application registration (a header-only/partial boot fails);
  `grep -a` handles the ANSI/control-laden console; the console is retained at
  `build/rtems-generic/qemu-console.log` (verified present, 4487 bytes, shows
  the banner, `6 applications registered` and the app-start/TM lines).
- **`emulated_run.sh` change**: `bash -n` clean; the docker-image-first branch
  is a reasonable fix for a host without QEMU and matches the image the tools
  ship.
- **Dockerfile change**: the `qemu-system-misc` package is the correct
  Ubuntu 24.04/Debian home of the `qemu-system-riscv64` binary; the third
  `sb-set-builder` invocation follows the established kernel-bset pattern
  (subject to R1-02's clean-build caveat).
- **Gate evidence (host, this session)**: `ctest --test-dir build/native`
  **19/19 PASS**; `python3 tools/scripts/trace.py ...` **PASS** (99
  requirements, 58 srs, 27 sss, 14 gaps, 51 lean theorems); `bash -n` clean on
  both scripts.

## 4. Conclusion

- [ ] APPROVED - no findings or Comments only
- [x] APPROVED WITH COMMENTS - Minor findings tracked to closure
- [ ] REJECTED - one or more Major findings

No Major findings. The toolchain file, script mechanics and Makefile targets are
sound and the QEMU run demonstrably reaches application registration; the
generic-BSP-only claim holds at the toolchain/BSP level. The two Minor findings
are (R1-01) the MPFS platform-configuration/identity leak into the "generic"
QEMU image, which makes the retained console partly a hardware fiction and
contradicts the "no MPFS assumptions/peripherals" framing, and (R1-02) the
toolchain image used for the PASS evidence not being reproduced from the frozen
Dockerfile, which leaves the T18/T20 qualification and the `QEMU PASS` evidence
row unsupported by a clean build. Both must be closed (norm N12) before M10 is
committed as closed; R1-02 in particular is an evidence-integrity condition.
